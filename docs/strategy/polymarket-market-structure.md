这份笔记不是复刻原文，而是把对我们做 BTC 预测市场模拟盘和未来实盘系统有用的机制整理出来。

## 一句话总览

Polymarket 不是一个纯链上 DEX，也不是一个纯中心化交易所。它更像是：

- 链下 CLOB 负责挂单、撤单、排序和撮合。
- 用户用 EIP-712 签名表达交易意图。
- Operator 把匹配结果提交到链上。
- 智能合约负责最终资产结算。
- Relayer 帮用户支付部分链上操作的 gas。

所以它的核心特征是“链下速度 + 链上结算 + 中心化撮合权 + 用户资产约束”。

## 1. 订单是签名意图，不是立即上链交易

在 Polymarket 上，下单通常不是直接广播一笔链上交易，而是签署一段结构化订单数据。这个订单会进入 Polymarket 的链下中央限价订单簿。

对我们做交易系统的影响：

- 下单成功不等于最终链上成交。
- 模拟盘里不能只记录“发出订单”，还要区分 `submitted`、`matched`、`settled`、`failed`。
- 未来实盘时，交易日志必须记录订单 ID、签名时间、撮合响应、链上 settlement 状态。

当前项目启发：

- 现在我们只做只读模拟盘，还没有订单状态机。
- 后续进入 paper trading loop 时，可以先设计状态字段，为实盘留接口。

## 2. 价格是 makerAmount / takerAmount 隐式表达

原文强调，底层订单结构不一定直接存一个简单的 `price` 字段，而是通过交换双方资产数量表达价格。SDK 可以让开发者传 `price` 和 `size`，但底层仍会变成数量关系。

对我们有用的理解：

- 价格不是孤立变量，它和份额数量、费用、撮合路径绑定。
- 回测时如果只用最后成交价，会低估真实执行复杂度。
- 实盘前必须理解 SDK 如何把 `price`、`size`、`side` 转成签名 payload。

## 3. Operator 是撮合与提交链上结算的核心角色

Polymarket 的撮合不是任何人都能随便在链上调用。链下撮合引擎决定哪些订单匹配，再由 Operator 把匹配结果提交到链上执行。

这个设计降低了公开 mempool 抢跑，但引入了新的系统假设：

- Operator 控制撮合提交路径。
- 用户不能通过提高 gas 来抢优先级。
- API 延迟、撮合排序、重启窗口会直接影响策略表现。

交易系统影响：

- 我们的机器人不能只考虑“价格到了没有”，还要考虑“这笔订单在系统里能不能被及时处理”。
- 高频 Taker 策略会受 Operator 和 Relayer 延迟影响。
- Maker 策略在速度上通常更有优势，因为挂单和撤单主要发生在链下。

## 4. Relayer 让用户免 gas，但不会让系统免延迟

Polymarket 官方文档确认，Relayer 会作为交易赞助者为经过 Relayer 的操作支付 gas。用户体验上像是免 gas，但实际链上状态改变仍然需要有人提交交易。

对我们有用的理解：

- “免 gas”不是“无成本”，成本被平台或机制吸收。
- 需要上链结算的路径仍可能出现延迟、失败、重试。
- 对自动化策略而言，gasless 更像 UX 优化，不是执行确定性保证。

未来实盘系统需要：

- 记录 Relayer / settlement 相关错误。
- 对链上确认做超时处理。
- 不把 API 返回成功直接当成最终成交。

## 5. 三种匹配路径：Complementary、Mint、Merge

Polymarket 的条件代币机制让它不只是简单的买卖双方换手。原文把匹配路径分成三类：

- `COMPLEMENTARY`: 买方和卖方直接换手，类似普通订单簿交易。
- `MINT`: 两个互补方向的买单可以共同注入抵押品，铸造 YES / NO。
- `MERGE`: 两个互补方向的卖单可以销毁 YES / NO，释放抵押品。

对交易者最重要的点：

- 预测市场流动性不是只来自已有持仓换手，也可以通过 mint 创建。
- 退出也不一定需要传统意义上的接盘买家，merge 可以释放抵押品。
- 市场生命周期可能从早期 mint、中期换手、晚期 merge 变化。

对我们系统的影响：

- 简单价格历史无法解释所有成交背后的资金流。
- 后续如果做 PnL 或聪明钱追踪，必须识别 Split / Merge / Redeem / trade 的不同现金流。

## 6. Split、Merge、Redeem 会让普通 PnL 算错

这篇文章最值得我们记住的一点是：Polymarket PnL 不能只看买卖成交记录。

原因：

- `Split`: 用 1 USDC / pUSD 换出 1 YES + 1 NO。
- `Merge`: 用 1 YES + 1 NO 换回 1 USDC / pUSD。
- `Redeem`: 市场结算后，赢家 token 赎回为 1，输家归零。

正确 PnL 需要把所有现金流合并计算：

```text
总盈亏 =
  卖出收入
+ Merge 收入
+ Redeem 收入
- 买入支出
- Split 支出
+ 当前持仓市值
```

对我们项目的直接影响：

- 当前回测只模拟简单买入和卖出，因此 PnL 是简化版。
- 如果以后追踪链上钱包或做聪明钱分析，必须把 Split / Merge / Redeem 纳入账本。
- 否则可能把真实盈利看成亏损，或把幻觉盈利看成优势。

## 7. 手续费是 p × (1 - p) 曲线，且 Taker 付费

Polymarket 官方文档确认，部分市场的 Taker fee 使用：

```text
fee = C * feeRate * p * (1 - p)
```

其中：

- `C`: 交易份额数量。
- `p`: 份额价格。
- Maker 不付平台交易费。
- Taker 付费。
- 费用在 50% 附近最高，越接近 0 或 1 越低。

对我们当前 BTC 策略的影响：

- 中间概率区间交易摩擦更高。
- 高频 Taker 策略必须把 fee 纳入 edge 计算。
- 当前配置里的 `fee_rate = 0.0` 只是临时简化，后续需要按市场费率改成动态费用。

后续代码任务：

- 拉取 fee-enabled 和 fee rate。
- 回测里加入 `p * (1 - p)` 手续费模型。
- 把信号里的 `min_edge` 改成必须覆盖 fee + slippage + 安全边际。

## 8. Negative Risk 主要影响多结果市场

Negative Risk 用于多结果市场。直觉上，做空某个候选结果，等价于做多其他所有结果的组合。Polymarket 使用 `NegRiskAdapter` 做价值守恒转换，提高资金效率。

对当前 BTC 方向的影响：

- 我们现在主要关注二元 BTC 价格市场，短期内不必优先实现。
- 如果以后做选举、体育、奖项或多结果宏观市场，需要重新学习。
- 多结果市场的套利和 PnL 复杂度显著高于二元市场。

系统设计提醒：

- 不要把二元市场的 PnL 和风险模型直接套到多结果市场。
- 市场对象需要标记 `binary` / `multi-outcome` / `negative-risk`。

## 9. Maker 与 Taker 的速度结构不同

原文指出 Maker 挂单/撤单主要是链下路径，通常比 Taker 吃单更快；Taker 需要触发匹配和链上 settlement 流水线，因此更容易受延迟影响。

对我们未来实盘很关键：

- 纯 Taker 抢机会策略很难长期有优势。
- Maker 策略可能获得速度、手续费和返利优势，但承担逆向选择风险。
- 突发新闻或 BTC 快速波动时，挂单可能被更快的信息流打穿。

风控启发：

- 实盘前要区分 Maker 风控和 Taker 风控。
- Maker 策略需要更严格的撤单、最大挂单时间、价格偏离保护。
- Taker 策略需要更严格的滑点和成交确认保护。

## 10. 匹配引擎每周重启，需要系统级处理

Polymarket 官方文档说明，匹配引擎通常每周二美国东部时间 7:00 重启，窗口约 90 秒，相关 API 可能返回 HTTP 425。

对系统的要求：

- 425 不是永久错误，应该指数退避重试。
- 模拟盘和实盘都要记录这类事件。
- 实盘时不要在维护窗口附近启动激进策略。
- 如果做 Maker，心跳和挂单清理机制需要特别关注。

当前代码启发：

- 我们已经对公开数据请求做了简单重试。
- 后续交易接口必须把 425 单独分类，而不是当成普通异常。

## 11. Ghost Fill：API 显示成交但链上失败的风险

原文提到 Polymarket V2 的重要改进之一是降低 Ghost Fill。Ghost Fill 的核心问题是链下撮合状态和链上资金状态在时间上可能不一致。

对我们非常重要：

- 未来实盘系统不能只相信 “matched”。
- 最终持仓必须以可靠账户/链上/官方状态为准。
- 风控不能因为“以为成交了”而继续开下一笔相关仓位。

未来实盘状态机建议：

```text
created -> submitted -> accepted -> matched -> settling -> settled
                                      -> failed
                                      -> expired
                                      -> canceled
```

## 12. 对我们项目的优先级变化

读完这篇文章后，项目优先级应该稍微调整：

### 近期必须做

- 在回测里加入动态手续费估算。
- 把 `min_edge` 改成扣除手续费和滑点后的净 edge。
- 增加更详细的交易记录字段：信号价格、执行价格、费用、滑点、退出原因。
- 加入本地行情缓存，减少公共 API 抖动。

### 模拟盘阶段要做

- 设计 paper order 状态机，即使暂时不下实盘也按真实订单生命周期记录。
- 每次扫描输出持仓、现金、未实现盈亏、已实现盈亏。
- 把 API 错误分成网络错误、维护窗口、数据缺失、市场不适合交易。

### 实盘前必须做

- 区分 Maker / Taker 策略。
- 实现订单状态确认，不把 API 初始响应当最终成交。
- 加入费用、滑点、成交失败和撤单失败处理。
- 设计 kill switch 和维护窗口保护。
- 明确资金放在 Deposit Wallet / Relayer 路径下的操作限制。

## 13. 给交易者的复盘问题

每次看到一个 BTC 预测市场机会，先问：

- 这是纯 BTC 价格市场，还是间接事件市场？
- 价格 edge 是否足够覆盖 fee、slippage 和失败风险？
- 我是 Maker 还是 Taker？这决定了速度、费用和逆向选择。
- 当前市场处于早期、中期还是晚期？
- 如果 API 显示成交但最终没结算，系统会不会误判持仓？
- 如果 90 秒维护窗口或连接断开，系统会不会继续错误下单？

## 结论

这篇文章对我们的最大价值，不是提供一个立即赚钱的策略，而是提醒我们：预测市场自动化交易的核心不是“看到价格就下单”，而是理解订单、撮合、结算、费用、PNL 和失败状态如何共同影响真实收益。

我们当前项目还在只读研究阶段，正好可以把这些机制提前写进模拟盘设计里。这样等未来进入小资金实盘时，系统不会因为基础账本、费用或订单状态理解不完整而犯低级错误。
